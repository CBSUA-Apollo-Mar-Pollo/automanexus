## Product Vision

Automa Nexus is a browser-based low-poly 3D automation and programming game.

The game is inspired by automation and programming-focused games such as Factorio and The Farmer Was Replaced, but its primary identity is built around **programming-driven automation**.

The player should gradually progress from manually interacting with the world toward building systems that can operate automatically through code.

The central gameplay loop is:

**Build → Program → Run → Observe → Debug → Improve → Automate**

The player should be encouraged to experiment with code, observe what happens in the simulation, identify problems, and iteratively improve their automation.

### Core Game Concept

The world contains resources, machines, entities, and systems that the player can interact with and eventually automate.

Potential gameplay systems include:

- resource gathering
- mining
- farming
- production
- machines
- automated workers
- programmable entities
- resource transportation
- world exploration
- procedural world generation
- environmental interaction
- enemies or hazards

These systems should be introduced incrementally.

Do not assume that every planned system already exists. The repository is the source of truth for what is currently implemented.

### Programming as Gameplay

Programming is a core gameplay mechanic rather than merely a developer tool.

The player should eventually be able to write programs that control parts of the game world.

Programming concepts may be introduced progressively, including:

- variables
- conditions
- loops
- functions
- data structures
- state
- events
- APIs
- algorithms
- automation
- more advanced system-design concepts

The programming experience should feel approachable and rewarding.

Avoid designing the game as if the player is expected to already be an expert programmer.

### Learning Through Systems

Automa Nexus is also intended to teach programming and eventually software-engineering concepts through gameplay.

The complexity of the player's systems should grow naturally.

For example:

simple automation → reusable functions → interacting systems → state management → larger automated systems → architectural thinking

Do not force educational concepts into gameplay when they do not make the game better.

The priority is still to make a coherent and enjoyable game.

### Design Direction

Automa Nexus should feel:

- creative
- experimental
- programmable
- systemic
- understandable
- low-pressure
- rewarding to iterate on

Avoid unnecessary mechanics that make the game stressful or complicated without improving the core automation experience.

The game should reward the player for understanding systems rather than simply reacting quickly.

### Development Direction

Automa Nexus is an evolving project.

Many game systems are intentionally not fully defined yet.

Therefore, distinguish between:

1. **Implemented behavior** — behavior that already exists in the repository.
2. **Current requirements** — behavior explicitly requested for the task.
3. **Future ideas** — concepts described in the product vision but not yet implemented.

Never implement future ideas simply because they are mentioned in this document.

When a feature is requested, first determine how it fits into the existing gameplay and architecture.

Prefer building a small playable slice over designing an entire future system upfront.

## Verification Before Completion

Before considering a task complete:

1. Inspect the existing implementation before changing it.
2. Prefer the smallest change that solves the requirement.
3. Verify assumptions against the actual codebase rather than guessing.
4. Run relevant tests, type checks, linting, and builds when available.
5. For gameplay changes, verify the affected behavior in the running game when practical.
6. Check for edge cases introduced by the change.
7. Check that error handling is appropriate.
8. Do not claim a task is complete if verification was not performed.
9. Do not introduce dependencies unless they are justified.
10. Do not silently change unrelated behavior.

## Security

Treat all external input as untrusted.

- Validate data at system boundaries.
- Do not expose secrets or credentials in client-side code.
- Do not trust client-provided authorization or state.
- Avoid unsafe dynamic code execution.
- Avoid unnecessary use of eval or equivalent mechanisms.
- Do not introduce dependencies without considering their security and maintenance implications.
- Preserve existing security boundaries when modifying code.

## Code Organization

Keep files focused and cohesive.

- Do not put unrelated responsibilities into the same file.
- Separate distinct domains, features, and responsibilities into appropriate modules.
- Prefer organizing code by feature/domain rather than creating arbitrary utility folders.
- Extract a module when a responsibility has a clear boundary or is independently understandable.
- Keep components focused on presentation and UI composition when practical.
- Move game logic, simulation logic, state management, and data transformations out of large UI components when they become distinct responsibilities.
- Avoid creating files or folders purely for the sake of splitting code.
- Do not create excessive fragmentation where understanding a feature requires jumping through many tiny files.
- Before creating a new file, determine whether it represents a meaningful abstraction or responsibility.
- Before adding code to an existing file, check whether that file already owns the responsibility being added.
- Preserve and follow the existing project structure and conventions.
